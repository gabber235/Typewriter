# Authoring writes from any client

> **Status: decided** (actor, tier A, tier B). The Open questions at the end are not decided. Every name marked *(proposed)* does not exist yet; every other name refers to existing code.

How any client writes authored state (entries, fields, resources, list items, records of any catalog type) to the realm through the one existing edit contract, `CommitPreparedEdit`. Related: [engines.md](engines.md#engine-communication) (engines write authored state directly), [stored-data.md](stored-data.md#transactions) (the optimistic transaction pattern this mirrors), [live-data.md](live-data.md#session) (sessions).

## Problem

Today only the panel writes authored state, and only the panel knows how:

- The contract is general. `PreparedEdit{catalog, expectations, intents}` (`skir-src/editor/v1/authoring.skir` `PreparedEdit`) carries ordered `EditIntent`s (`authoring.skir` `EditIntent`) and the original facts they relied on (`authoring_facts.skir` `EditExpectation`). Admission (`SurrealAuthoringRepository.kt` `admit`) compares facts, plans, derives the **required** guards itself (`EditExpectations.kt` `requiredExpectations`) and rejects any edit that lacks one with `missing_expectation` (also in `admit`).
- The knowledge to build a valid edit lives in two places: the panel's Dart model (`panel/lib/authoring/application/authoring_expectations.dart`, `realm_edit_model.dart`) and the realm's in process path (`WorkingViewEditContext`, `AuthoringPlanningSession`, used by `RealmStructureProvisioning.kt` `ensure`). Neither is usable by another service.
- Reads are all or nothing. `QueryAuthoringState` (`authoring.skir` `QueryAuthoringState`, `AuthoringState.findings`) returns every resource and link of the realm and every finding set with findings, an unfinished outcome, or an outdated status, each judged against the reply's view first (`FindingFreshness.kt` `forReply`); a check missing from the list has no findings known: it is clean, or it has not run yet. A set's evidence is `CheckEvidence` (`checking.skir` `CheckEvidence`): `fact` entries hold an `EditExpectation` an editor can judge, `scope` entries record a name lookup only the realm judges.
- Only `organization_member` (a panel user) may call the authoring routes (`transport-routes.yaml:465-525`).
- The realm does not know who committed. Realm routes have no caller identity in the subject, and handlers see only `IncomingUnaryCall{address, request, headers, ...}` (`CommunicatorRouter.kt` `IncomingUnaryCall`).

Two kinds of clients need to write:

1. **Generic services** (a future MCP server). Only the catalog and the wire contracts; no generated Kotlin types for extension entries.
2. **Engine and extension code** (Paper, in game tools, recording). KSP generated types for every entry and record; they want typed, ergonomic helpers.

## Overview

| Tier | Who uses it | Knows | Gives |
| --- | --- | --- | --- |
| Actor | every commit | transport credential | verified principal plus on behalf chain |
| A: generic SDK *(proposed module `typewriter-authoring-client`)* | any Kotlin service; wire shape for other languages | catalog only | scoped reads, path writes, catalog driven values, guards, commit, rerun, batching |
| B: generated helpers | engines, extensions | KSP types | typed drafts, native encode, typed create and insert |

Tier B adds no new mechanism: it is codegen over tier A, the same way `XDraft.setX` (generated by `DraftEmitter.kt:139-163`) is codegen over `EditContext.set`.

The core move: **extract the realm's in process edit machinery into a shared library** and make it work over a scoped view. Realm provisioning, operations, the SDK and the engines then build edits with the same code that admission uses to check them.

## The actor

### Principles

- The **principal** is derived server side from the transport credential. A payload never names its own principal.
- A principal is open: `kind` plus `id`. User, service, host and future kinds fit with no contract change.
- **Initiated by** is a plain statement a trusted service adds (the player behind an in game capture). It is recorded for history and display, never used for authorization: a service that may write anything gains nothing by lying about it.
- A service acting for a user (an MCP server) logs in as that user through delegated login, so its principal is the user and needs no special case.
- Permission checks for a player's in game writes happen in the engine, which knows the player, before it writes.

### How the backend already knows the caller

- Panel connections: the permission component grants the user's own scope and reply inbox (`backend/access/auth-typewriter-permissions/src/users.rs:95-127`, `panel_reply_inbox_prefix(&actor, ...)`).
- Services: grants come from the service's messaging scope; an owned realm gives `realm_coordinator` and `realm_participant`, an attached realm gives `realm_participant` (`services.rs:171-189`).
- Roles declare a `personal` identifier that the grant generator binds into subjects (`transport-routes.yaml:19-23`; `services/protocol/skir-gen/src/routes/grants.ts:72-82`). `authenticated_user` and `organization_member` bind `user`; `registered_service` binds `service`; the realm roles bind nothing.

The broker enforces publish permissions. So a subject token bound from the caller's own grant **is** verified identity, as strong as the credential. The reply inbox is not: a publisher sets `reply_to` freely.

### Proposal: caller bound subjects

A route opts in with `caller: bound` *(proposed key)*. The generator appends the caller's personal identity to the request subject:

```yaml
roles:
  realm_participant: { side: service, tenant: [organization, realm], personal: service }   # proposed: personal added
  realm_coordinator: { side: service, tenant: [organization, realm], personal: service }   # proposed: personal added

  - name: authoring_edit_commit
    scope: realm
    caller: bound                                        # proposed
    callers: [{ role: organization_member }, { role: realm_participant }]
    server: { role: realm_coordinator }
```

```
service.to.{realm}.organization.{organization}.realm.by.user.{user}.editor.authoring.edit.commit
service.to.{realm}.organization.{organization}.realm.by.service.{service}.editor.authoring.edit.commit
```

Each role's grant binds its own personal token, so a service cannot publish under another service or a user. The router parses the token into the call:

```kotlin
data class IncomingUnaryCall<Address : Any, Request : Any, Response : Any>(
    val address: Address,
    val request: Request,
    val caller: PrincipalId?,          // proposed: present on caller bound routes
    val headers: MessageHeaders,
    // ...
)
```

A new principal kind (a host, a future agent kind) is a new identity in the generator (`manifest.ts:25-30`, `subject.ts:4`) and a grant in the permission component. The Skir contract does not change.

- `PreparedEdit` stays as is: it is also embedded in `TypeArgumentChangePreview` and `PreparedEditReady`, where an actor makes no sense.
- Examples: a panel user: `Actor{user:u1}`. An engine committing a player's capture: `Actor{service:paper-1, initiated_by: protagonist:abc}`. An MCP server: it logs in as the user, so `Actor{user:u1}`. Realm provisioning in process: `Actor{service:<realm service>}`.
- `initiated_by` from a non service principal is `forbidden_error`.
- `forbidden_error` also covers a later realm side policy on which principals may author (team management, beta).

### Alternatives considered

| Option | Verdict |
| --- | --- |
| Actor enum (panel user, player, engine) | rejected by the brief; every new kind changes the contract |
| Principal in the payload, trusted | spoofable |
| Reply inbox as identity | spoofable, `reply_to` is free |
| Backend signed token in the payload (JWT from the permission component) | works and is transport independent; needs key distribution to realms and expiry handling. Keep as fallback if subject binding meets limits |
| NATS server side request info headers | ties identity to NATS account layout; auth callout users are not separate accounts today |

## Tier A: generic SDK

### Shared machinery

Move from `services/runtime/realm` into the proposed module `services/sdk/typewriter-authoring-client` (or into `typewriter-api`, see open questions):

- `requiredExpectations` and `sameFact` (`edit/EditExpectations.kt:24-195`)
- `AuthoringPlanningSession` and `AuthoringMutationPlanner` (`edit/AuthoringPlanningSession.kt`, `edit/AuthoringMutationPlanner.kt`)
- `WorkingViewEditContext` (`edit/WorkingViewEditContext.kt`), generalized from `AuthoringView` to `AuthoringBaseline` *(proposed interface)*: catalog, observation id, the resources in scope, their links
- the parts of `ResourceValueMapper` and `CurrentAuthoringValues` that read values and links

Admission keeps calling the same `requiredExpectations`. Client and server can no longer drift.

### Kotlin API

```kotlin
package com.typewritermc.authoring.client // proposed

/** One realm, seen by one principal. Implementations: routed (any service) and in process (the realm itself). */
interface RealmAuthoring {                                            // proposed
    suspend fun catalog(): AuthoringCatalog
    suspend fun read(scope: AuthoringScope): ScopedRead
    suspend fun prepare(target: PreparationTarget, supplied: DataValue? = null): PrepareValueResult
    suspend fun commit(edit: PreparedEdit, initiatedBy: PrincipalId? = null): CommitPreparedEditResponse
}

/** The checked catalog of one generation, built from FetchEditorCatalog. */
class AuthoringCatalog(                                               // proposed
    val generation: CatalogGeneration,
    val checked: CheckedCatalog,
    val relations: List<RelationContract>,
) {
    fun type(id: TypeDefinitionId, arguments: List<TypeUse> = emptyList()): NamedTypeUse
    fun schema(use: TypeUse): Resolution<CheckedType>
    fun schemaAt(record: AuthoringRecord, path: ValuePath): Resolution<CheckedType>
    fun concreteForms(of: TypeDefinitionId): List<NamedTypeUse>
}

/** Converts portable JSON (what an MCP tool receives) to a DataValue of [expected], with schema problems. */
fun AuthoringCatalog.valueFromJson(expected: TypeUse, json: JsonElement): ValueResult            // proposed
fun AuthoringCatalog.validate(expected: TypeUse, value: DataValue): List<ValueProblem>          // proposed

sealed interface ValueResult {                                        // proposed
    data class Valid(val value: DataValue) : ValueResult
    data class Invalid(val problems: List<ValueProblem>) : ValueResult
}

/**
 * Runs [block] against a fresh scoped read, commits its intents as one PreparedEdit, and reruns the whole
 * block on conflict_error with a new read, like apply() on stored data. Reads inside the block become
 * expectations; required guards are added automatically.
 */
suspend fun <R> RealmAuthoring.edit(                                  // proposed
    scope: AuthoringScope,
    initiatedBy: PrincipalId? = null,
    attempts: Int = 5,
    block: suspend context(AuthoringTransaction) () -> R,
): EditOutcome<R>

sealed interface EditOutcome<out R> {                                 // proposed
    data class Committed<R>(val result: R) : EditOutcome<R>
    /** Invalid edit, conflicts after every attempt, or no right to write; `problems` is empty unless the edit was invalid. */
    data class Refused(val message: String, val problems: List<ValueProblem>) : EditOutcome<Nothing>
}
```

Authored writes stay a block and do not become transaction functions (decided 2026-11-04). The two have different needs: a stored write can run hundreds of times per tick across servers and must never be lost, so the realm decides it and the engine predicts it. An authored write runs a few times per second at most, and a lost one is no tragedy, so it runs on the writer and sends the result. They share only the words `Committed` and `Refused`.

The transaction is the existing `EditContext` (`typewriter-api/.../authoring/EditContext.kt`) plus untyped path access. Because it **is** an `EditContext`, every generated `XDraft.setX` works inside it unchanged.

```kotlin
interface AuthoringTransaction : EditContext {                       // proposed
    val authoringCatalog: AuthoringCatalog

    /** Untyped reads; each records a value expectation. */
    fun value(at: ValueLocation): DataValue?
    fun record(id: ResourceId): AuthoringRecord?
    fun items(at: ValueLocation): List<ListItem>
    fun resources(type: TypeDefinitionId): List<ResourceId>

    /** Untyped writes; checked against the catalog and the staged graph before commit. */
    suspend fun set(at: ValueLocation, value: DataValue)
    suspend fun insert(at: ValueLocation, value: DataValue, after: ItemId? = null): ItemId
    suspend fun create(type: NamedTypeUse, fields: Map<String, DataValue> = emptyMap(), id: ResourceId = ResourceId.random()): ResourceId
    suspend fun createRecord(type: NamedTypeUse, fields: Map<String, DataValue> = emptyMap()): DataValue
}

/** Path building on top of the existing ValueLocation helpers (TypedPath.kt). */
fun ResourceId.at(vararg fields: String): ValueLocation =            // proposed
    fields.fold(ValueLocation.of(this)) { location, name -> location.field(name) }
```

- `create` and `createRecord` call the realm's `PrepareValue` (`catalog.skir:352-354`, route `editor_value_prepare`) for defaults, then overlay `fields`. Native defaults are code inside extension artifacts; only the realm and hosts with those artifacts can run them. A host with generated bindings prepares locally with `DefaultInitializationRuntime` as `RealmStructureProvisioning.kt:122-129` does.
- `ItemId`s are allocated client side, deterministic per attempt, as `WorkingViewEditContext.insert` does today.
- **Batching** is the block: everything staged before it returns is one `PreparedEdit`, one atomic commit.

### Guard collection

At the end of the block:

```kotlin
val (edit, plan) = session.finish()
val required = baseline.values.requiredExpectations(edit, baseline.resources, baseline.relationIds, plan)
edit.copy(expectations = (capturedReads.observations() + required).distinct())
```

This is `WorkingViewEditContext.finish()` unchanged, over a scoped baseline. The scoped read must contain every fact `requiredExpectations` touches: each written resource, its configuration chain, and its links for every relation. The scope request therefore always widens to "resources written plus their link projections" (see below).

## Worked examples

### 1. MCP service: set a field by path, create an entry (catalog only)

```kotlin
class AuthoringTools(private val realm: RealmAuthoring) {
    suspend fun setField(resource: ResourceId, path: List<String>, json: JsonElement): ToolResult {
        val outcome = realm.edit(AuthoringScope.resources(listOf(resource))) {
            val at = resource.at(*path.toTypedArray())
            val record = record(resource) ?: return@edit ToolResult.notFound(resource)
            val expected = when (val schema = authoringCatalog.schemaAt(record, at.path)) {
                is Resolution.Ready -> schema.value.use
                is Resolution.Invalid -> return@edit ToolResult.unknownField(path, schema.diagnostics)
            }
            when (val value = authoringCatalog.valueFromJson(expected, json)) {
                is ValueResult.Valid -> set(at, value.value).let { ToolResult.ok(at) }
                is ValueResult.Invalid -> ToolResult.invalid(value.problems)
            }
        }
        return outcome.toToolResult()
    }

    suspend fun createEntry(type: TypeDefinitionId, fields: Map<String, JsonElement>): ToolResult {
        val catalog = realm.catalog()
        val use = catalog.type(type)
        val values = fields.mapValues { (name, json) ->
            val field = catalog.fieldType(use, name) ?: return ToolResult.unknownField(listOf(name))
            (catalog.valueFromJson(field, json) as? ValueResult.Valid)?.value ?: return ToolResult.invalidField(name)
        }
        return realm.edit(AuthoringScope.resources(emptyList())) {
            ToolResult.created(create(use, values))
        }.toToolResult()
    }
}
```

The MCP service logs in as the user, so its commits carry the user as principal. `catalog.fieldType` *(proposed)* reads `AppliedSchema.fields`. The tool layer never sees `EditExpectation`.

### 2. In game capture: write the player's Position into a field

Common captures use the core `Capture` event ([capture.md](capture.md)); this form is for custom steps.

```kotlin
class CapturePositionTool(private val realm: RealmAuthoring) {
    suspend fun capture(player: PaperPlayer, entry: ResourceId, origin: Origin) {
        val position = player.bukkit.location.fromPlatform<Position>()
        val outcome = realm.edit(
            scope = AuthoringScope.resources(listOf(entry)),
            initiatedBy = origin.principal,
        ) {
            when (val draft = TeleportActionEntry.draft(entry)) {
                is Availability.Available -> draft.value.setTo(Var.value(position))
                is Availability.Unavailable -> error("Entry $entry is not a teleport action")
                is Availability.Failed -> error(draft.diagnostic.toString())
            }
        }
        when (outcome) {
            is EditOutcome.Committed -> player.sendMessage("Captured position into ${entry.value}")
            is EditOutcome.Refused -> player.sendMessage("Capture refused: ${outcome.message}")
        }
    }
}
```

The tool runs from a handler that asks for `origin: Origin` and passes it on, so `initiatedBy = origin.principal` names whoever caused the occurrence ([events-and-handlers.md](events-and-handlers.md)). Capturing a type's value is an event owned by that type, such as `CaptureLocation` ([panel-engine-communication.md](panel-engine-communication.md) question 6); this tool only shows the write. The panel needs no open tab; `AuthoringChanged{actor}` tells open panels who changed the entry.

### 3. Road network tool: insert and update node records

```kotlin
class RoadNetworkTool(private val realm: RealmAuthoring, private val network: ResourceId) {
    suspend fun addNode(at: Position, after: ItemId?): ItemId? =
        realm.edit(AuthoringScope.resources(listOf(network))) {
            val draft = RoadNetwork.draft(network).orThrow()
            draft.insertNodes(RoadNode(position = at), after = after)
        }.committedOrNull()

    suspend fun moveNode(node: ItemId, to: Position) =
        realm.edit(AuthoringScope.resources(listOf(network))) {
            val nodes = RoadNetwork.draft(network).orThrow().nodes.orThrow()
            nodes.item(node).orThrow().setPosition(to)
        }

    suspend fun widen(nodesToWiden: Set<ItemId>, radius: Double) =
        realm.edit(AuthoringScope.resources(listOf(network))) {
            val nodes = RoadNetwork.draft(network).orThrow().nodes.orThrow()
            nodes.items().orThrow().filter { it in nodesToWiden }.forEach { id ->
                nodes.item(id).orThrow().setRadius(radius)
            }
        }
}
```

`widen` stages one `set_value` per node; all of them commit together or none do.

### 4. NPC recording: one batched commit when recording stops

```kotlin
class NpcRecorder(private val realm: RealmAuthoring, private val cinematic: ResourceId) {
    private val frames = mutableListOf<NpcKeyframe>()
    private var startedAt: Duration = Duration.ZERO

    fun tick(npc: PaperNpc, elapsed: Duration) {
        frames += NpcKeyframe(at = elapsed, pose = npc.entity.location.fromPlatform<Pose>(), swing = npc.swinging)
    }

    suspend fun stop(npc: Npc, recordedBy: PaperPlayer): EditOutcome<ItemId> {
        val segment = NpcRecordingSegment(npc = npc, start = startedAt, keyframes = frames.toList())
        return realm.edit(
            scope = AuthoringScope.resources(listOf(cinematic)),
            initiatedBy = recordedBy.principal,
        ) {
            val draft = CinematicEntry.draft(cinematic).orThrow()
            val last = draft.segments.orThrow().items().orThrow().lastOrNull()
            draft.insertSegments(segment, after = last)
        }.also { if (it is EditOutcome.Committed) frames.clear() }
    }
}
```

One intent carries the whole segment; the binding allocates an `ItemId` per keyframe inside the encoded `ListPayload`. A long recording can exceed `request_max_bytes` (512 KiB, `transport-routes.yaml:16`), so `authoring_edit_commit` must raise its request ceiling (framed requests already exist).

### 5. Conflict and rerun

Two builders add road nodes after the same node at the same moment.

```kotlin
val first = async { tool.addNode(firstPosition, after = n2) }    // nodes = [n1, n2], inserts after n2
val second = async { tool.addNode(secondPosition, after = n2) }  // nodes = [n1, n2], inserts after n2
```

What happens:

1. Each insert guards only its `after` anchor: `exists{at: network.nodes + ItemPathSegment(n2), expected: true}`. This is the **required** guard for `insert`, so a client could not omit it; nothing guards the whole list.
2. Both commit; neither conflicts. The two new nodes land after `n2` in commit order.
3. A rerun happens only when the anchor was removed: if another edit removed `n2` first, the insert gets `conflict_error` on its `exists` guard, and `edit` reruns the block on a fresh scoped read. A tool that means "append" reads the last item **inside** the block, as example 4 does, so the rerun picks an anchor that still exists.
4. After `attempts` conflicts the outcome is `Refused`.

Rule (as for transaction functions): every decision that depends on authored state belongs inside the block.

### 6. Failures

```kotlin
when (val outcome = tools.setField(entry, listOf("to", "wrold"), json)) {
    // Unknown field: caught before commit by the catalog (schemaAt), no network write.
    is ToolResult.UnknownField -> reply("No field ${outcome.path.joinToString(".")} on ${entry.value}")
    else -> reply(outcome.toString())
}

val outcome = realm.edit(AuthoringScope.resources(listOf(section))) {
    delete(section)   // a realm section owned by the realm root
}
when (outcome) {
    // Refused by the planner or admission: invalid intent, broken relation rule, missing guard, no right to write.
    is EditOutcome.Refused -> log.warn(outcome.message) // owner_required
    is EditOutcome.Committed -> Unit
}
```

Catalog changed: the client sends `catalog = G1`; an extension reload produced `G2`; admission answers `catalog_changed_error(G2)` (`SurrealAuthoringRepository.kt:62-66`). `edit` fetches the `G2` catalog, rereads, and reruns the block once. If the field no longer exists in `G2`, the typed draft read returns `Unavailable` or the path write is rejected with `ValueProblem`, and the outcome is `Refused`. A catalog change never counts toward `attempts`.

A missing guard (`missing_expectation`) means a client bug in a non SDK client; the SDK cannot produce it because it uses the same `requiredExpectations` as admission. A scoped read that missed a fact (for example a link outside the scope) is the one exception, covered by the scope widening rule.

## Costs

- **Extraction** is the largest item: about 1,000 lines of realm edit code plus the read helpers it depends on (`authoring/` is about 4,400 lines; only part moves). It must lose its dependency on the full `AuthoringView`.
- **Scoped planning is weaker than admission.** Rules that need the whole realm (`singleton_exists`, relation cycles across unread resources) can only be checked by the realm. The client planner reports what it can; admission stays authoritative, and such rejections arrive as `Refused` after a round trip.
- **List guards.** Today an insert guards the whole list value; the settled change (Open 8) guards only the named items, a change to `requiredExpectations`, admission, and the 15 files using `resource_exists`.
- **Transport generator work** for caller bound subjects, plus a second principal kind in grants.
- **`valueFromJson`** is a new converter over every `ResolvedRepresentation` (scalar, record, sequence, mapping, link, named wrappers).
- **`EditorCatalog` to `CheckedCatalog`**: a generic client needs a checked catalog. Whether `FetchEditorCatalog` carries enough to build `DefaultCheckedCatalog` needs verification.
