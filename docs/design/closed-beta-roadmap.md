# Closed beta roadmap

Source design: the topic files in docs/design/ (start at overview.md) and docs/vision/.

Milestones, used the same way in every design record: **alpha** is the first closed beta release (this PR stack); **beta** is added during the closed beta; **after** comes after the closed beta; **someday** has no plan.

## Decided

- Shape: a stack of self contained PRs on top of the agent harness and test review stack. Each PR ends in a simple but realistic Paper demo, informed by the legacy BasicExtension (a showcase, not a full port), with tests. Lower PRs get built while higher ones are still being designed and planned.
- Goal of the full stack: a few entries demo every primitive and the core functions (scenes, audiences, commands, dialogue, events, ...).
- 2026-10-30 additions: interaction bounds; debug and inspect (late, before migrations); a conversion track for legacy extensions starting around layer 20 (WorldGuard is not converted; the region extension from #522 replaces it).
- Scope includes items not yet designed: configurations (root resource replacing configs and snippets), artifacts and assets, and core needs revealed by develop PRs (#521 visibility, #522 region, road network).

- Workflow (2026-11-01): two tracks run side by side. The rough design track (planning phase 2) works bottom up through every layer, M1 first, then M2: an audit lists contradictions, implicit gaps, and pieces that fail the coding principles; each finding is settled one topic at a time or left Open on purpose. The detailed plan track (planning phase 3) plans one layer once the layer below it is built, so planning sees the complete rough picture. The coordinating design thread runs the rough design track; each layer's detailed plan, build, and merge run in their own thread, and their results are reconciled back into these records before the next step.
- Layer 0 (base) is the agent harness and test review stack: #542 (xtask toolchain, two test tiers, worktree stack, generated setup builders, panel integration harness, TestRun results), #543 (secrets), #546 (composable test kits, full stack panel scenarios, full CI tier, idempotent Realm commits with resend). It adds no engine or Paper runtime; layer 1 starts from the current realm and engine code.
- Demo exception (2026-11-02): layer 1 (formula core) ends in a realm only demo instead of a Paper demo: formulas checked in the existing check list and pure formulas evaluated in the realm, proven by tests. No Paper runtime (3) or formula editor (2) exists below it.

- Design contradictions are settled by the first layer that needs them, before that layer is built:
  - single writer for a running step, settled 2026-11-03: there is none; every stored write is a realm transaction, and local step values, checkpoints, the home engine, and the lease are removed: layer 3 (sessions).
  - `ItemRef` as an identity: layer 6 (stored data).
  - where the decision runs when one event reaches several engines: layer 4 (event core).
  - record keys for `Due<E>`: layer 7 (time and reactions).
  - purpose of `BookScope` next to `PublishScope`: layer 13 (book variables and instances).

- Todo, designed by the layer that first needs it (found while sketching panel emits, [panel-engine-communication.md](panel-engine-communication.md)):

  - formula `now` and `random` (2026-11-02): what `now` is in a `Changes` field evaluated before commit and possibly on an engine, and what seeds `random` outside an interaction (`PublishScope`, `DefinitionScope`, `TypeScope`): layer 7 (time and reactions).

  - merging the results of one event that ran on several engines into one `Done`, `Denied`, `Failed`, or `NotHandled` (part of the decision contradiction above): layer 4 (event core).
  - every engine holding a session of the subject answers an event that asks for a result, also without a handler, so `NotHandled` does not have to wait for a timeout; an engine that lacks the event's exact `TypeDefinitionId` (type and revision) or cannot decode it answers `Failed(reason)`, never stays silent: layer 4 (event core).
- Query graph over growing `ReverseDependencyIndex` (2026-11-01): the query graph is the one tracked read mechanism for realm checks and searches; authored reads and stored reads (type plus partial key) are both inputs, and a stored commit reruns what read it like an edit does. It replaces `ReverseDependencyIndex` and the `EditExpectation.dependencies()` mapping (`InputDependencies.kt`). Layer 1 builds it for formula checks; layer 6 adds stored reads. In layer 1 the graph becomes the only rerun mechanism for every realm check (2026-11-02): each check run is a query whose recorded `InputIdentity` reads are its inputs, `CheckContext` stays unchanged for check authors, and `ReverseDependencyIndex`, `DefaultReverseDependencyIndex`, `EditExpectation.dependencies()`, `RealmCheckRuntime.invalidateCurrent` and the uncalled `invalidate(changed)` are deleted. The graph takes its input changes from the `AuthoringViewDelta` applied at view install, so commits report nothing extra (2026-11-02); the graph revision decides finding currency in `EditorUpdatePublisher` and publication acceptance (shape in formula-language.md, Query graph). `EditExpectation` stays as the commit guard; searches join in layer 10. Needs: migration dry runs (migrations.md) and reported id checks and searches (panel-engine-communication.md question 10).
- The roadmap is not fixed: layers are reordered, inserted, or reprioritized as design work discovers needs.
- Order v5 (2026-11-01): engine communication is designed before Minecraft value types and built as its own layer 9, after the mirrors it needs; Minecraft value types (10) follow it and absorb capture, because capture is an event owned by the types. Going to a captured value (C6: teleport and highlight) and server drawn visuals need holds and land together in 25. Layer 3 delivers the `Engine` identity and the panel engine as session reporter only; the emit forwarder is part of layer 9. Waiting modes (pick a block, place corners) need holds and stay with in game editor tools (25). Within one milestone, layers stay whole: reorder layers rather than split work that lands in the same milestone. Scenarios and milestones: [panel-engine-communication.md](panel-engine-communication.md).
