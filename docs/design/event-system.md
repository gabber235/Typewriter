# Event system design (direction C)

Phase (2026-10-29): feasibility. The goal is to check that every legacy and vision feature CAN be represented with the primitives. Feature sketches (NPCs, commands, audiences, quest item) are not designs; their details are decided when that feature is built. Primitive level decisions below are the real output.

Working decisions, made together. Code in `design-exploration.md` and `compare.html` is pseudocode and not binding.

## Decided

- Direction C: typed handlers whose parameter types decide when they run. It has an ECS feel, but it is not mapped strictly onto ECS.
- A handler asks for the event plus parameters; each parameter type is resolved by a parameter kind (stored values, holds, identities, live capability traits, `Runtime`, `Formula`, `Candidate`, `Member`, ...).
- Parameters resolve from the event's subject by default, else from the event's only field of the identity kind the stored value lives on (typed roles when an event has two of one kind, see identity resolution):

```kotlin
@Handler
fun NpcClicked.talk(talk: Talking, mood: Mood) = ...
```

- If any parameter cannot be resolved, the handler does not apply.
- A stored value has an owner by default (a step, interaction, or book instance) and is removed automatically when the owner ends, so it cannot leak after a crash, server move, or hot publish. Extension code may add an ownerless stored value as an escape hatch.

- Parameter types decide where a handler runs. A handler that asks for live traits runs on the engine where its subject is live. A handler that asks only for stored data runs once, where the event happened. The realm sees this statically, and the panel catalog can filter on required capabilities.

- The return type decides the phase. `Verdict` handlers take part in the decision (pure; a follow up runs when the final outcome matches its verdict). `Unit` handlers run after the event was allowed. Non cancellable events (tick) accept only `Unit` handlers.
- Variants (Java chat versus Bedrock form) are picked by the step when it starts, by adding a different stored value. No "most specific handler wins" rule.
- Formula fields shown to the protagonist (dialogue text) are read by the display derive and are live (superseded the evaluate once rule; see hot publish).
- Raw input becomes intent events (`Confirm`). Which raw key confirms depends on what currently holds the protagonist's input (develop: `Confirmations`, `ConfirmationInput`), so a raw key is only taken when it is the offered key.
- Verdicts are allow, deny, change, and pass. Pass means "not my business" and never overrides a lower priority decision.
- No separate derived-value concept: extensions declare formulas in Kotlin (inputs may be stored values or other formulas). Handlers read them as `Formula<T>` parameters, always current. Formulas stop propagating when the value is unchanged, and derives run only after all formulas settled.
- `@Derive` with a `Hold` result (a function returning `Hold?`; a `Stored` result is covered under state change starts). While it returns a Hold, the system holds it; when it returns null or another Hold, it removes or reconciles (`Removed<H>`, `Changed<H>`). Holds are compared by value, so an equal Hold from the next step means nothing is undone (handover). Holds are never saved: a crash leaves nothing to undo. Hold derives only touch the engine-side view (attributes, packets, camera), never stored data. Stored derives are pure over tracked inputs and an equal result writes nothing; a cycle between derives is a realm check diagnostic. Derives are the runtime behind manifest entries and legacy audiences. `Added<H>` and `Removed<H>` handlers and `restore` must be safe to repeat.
- Owners (step, interaction, book instance) are identities, with a generation so an event for a finished step is dropped. A step belongs to a group (`step.group`). Events can address a step: `fun Confirm.advance(talk: Talking)` (the step is the event's only `Step` field).
- Live values (offered key in the hint) are `Formula<T>` parameters of the render handler.
- A Hold has a stored snapshot captured on first start (`snapshot()`) and `restore(snapshot)`; nothing else (see hold hooks). Content can overwrite the snapshot, for example to land the protagonist somewhere else after a camera, with one teleport.
- The filming protagonist is hidden by packets, not an invisibility potion (nothing persisted, nothing to restore).
- Interaction (the running group of steps): created when a start fires into an entry that is not a member of a running interaction. Membership is computed at publication as every entry reachable from the start through trigger links, crossing book edges. Entries that take time (dialogue, scene, delay, search then click) are steps; a delay is a step. Instant entries run inside the interaction. An interaction ends when no step runs and nothing is pending in any branch.
- Holds have no owner. When a derive stops returning a Hold, its removal (`Removed<H>`, `restore`) waits a short grace (default about 10 ticks, half a second), set per Hold type and overridable by content. An equal Hold for the same protagonist within the grace, from any interaction, adopts it and its snapshot.
- Lane = Hold type. No separate lane concept. Publication knows statically which Hold types a step can produce (step stored values, derives, Hold types).
- Forwarding is declared by the trigger type (the extension marks it forwardable).
- Clashes (rules apply at every step start): the incoming step declares Drop (default), Queue, or Replace (`onClash`, a normal entry field that is the default of the `startStep` argument). The running step can carry a `Protected` stored value (whole step or a period). Replace wins only against lower inherited priority; Replace against Protected becomes Queue. Replace ends the whole running interaction.
- A queued step gives up through a formula (for example `waited > 10s || !protagonist.in_region(arena)`), and also when its book stops applying or its interaction ends.
- Server wide events are normal steps; the creator decides per event through the clash field.
- `Candidate<E>` parameter: the handler runs once per published entry of type `E` whose book applies to the subject (instances are separate entries). The verdict carries that entry's inherited priority. With a stored value from a step, priority is the step entry's; pure extension handlers get a low default.
- Verdict resolution: drop passes; changes apply from low to high priority (each a pure function, higher sees lower's result); allow versus deny is won by the highest priority; a tie means deny wins at runtime; the tie itself is reported by a realm check (the existing checks subsystem, `RealmCheckProvider`, reporting diagnostics), not by the event system; never undo a foreign deny; every verdict may carry a follow up (`deny { }`, `allow { }`, `pass { }`), and a follow up runs when the final outcome matches its verdict (deny on denied; allow and pass on allowed). Two cancelling entries both fire their triggers, like legacy; clash rules settle competing starts. `pass(on = Allowed | Denied | Any) { }` chooses when a pass follow up runs (default Allowed; `Any` gets the `Outcome`), so one handler holds the decision and every reaction. The `Outcome` parameter stays for Unit handlers that never decide.
- Triggers are ordinary handlers: `fun PlayerChat.containsText(trigger: Candidate<PlayerMessageContainsTextEventEntry>) { if (trigger.matches(this)) trigger.triggers.fire(context) }`. Extra needs are extra parameters (traits, stored values, formulas). Entries stay plain data. `fire` makes the core follow the entry's trigger links; trigger code only says it fired.
- By default a trigger only sees allowed events. A handler that asks for an `Outcome` parameter also sees denied ones. Deny and start goes through a deny follow up, so it only starts if that deny wins.
- The entry type declares what it produces (`: Produces<ChatMessage>`); `entry.triggers.fire(...)` only accepts that type and carries it as a typed produced record (`ChatMessage(message)`). Produced records are formula context flowing along links (vision: link context = formula context); later formulas in the chain read them with checking and autocomplete (`{chat.message}`). When several paths reach an entry, a record is non-null if every path provides it, otherwise nullable (`chat?.message`).
- Events without a subject (Tick, world events): parameters become a query; the handler runs once per match (`fun Tick<EveryTick>.type(speaking: Speaking)` runs per step with that stored value).
- `Member<P>` parameter: runs once per member of the step's group, on that member's engine.
- Party dialogues: the dialogue entry has a creator field `advance: Anyone (default) | Everyone | Leader`.
- Each interaction has one home engine. Stored only handlers for its steps run only there; `Member<P>` handlers run on each member's engine. The home starts where the interaction started and follows the leader (or the majority) when members move.
- Guideline: store moments, not counters (`startedAt`, `skippedAt`), so steps rarely write. At runtime, stored values of a running step are local on the home engine (single writer) and saved to the realm at checkpoints (server move, step end, every few seconds).
- Verdict handlers never suspend (they run inline, e.g. inside a Paper event, reading cached stored data). `Unit` handlers may suspend.
- Extensions declare their own events in common code; events without a source are emitted by handlers. `emit()` queues: the emitted event is decided after the current event finishes (no nesting).
- One event type per meaning. What a delivery can do (decide, change, thread) is typed on the source, not the event.
- Threads are never "the main thread": live access runs on the thread that owns the identity (protagonist, entity, region), so Folia style region threads work.
- One occurrence can reach several sources (packet and Paper event can both decide and change); dedupe is decided below (meaning rule, occurrence dedupe key). "Sources must not overlap" was rejected. Open: the same occurrence reaching a handler twice through forwarding.
- `Hold.apply()` is rejected: view changes are normal handlers that take the Hold type as a parameter (a parameter that stays true through grace and adoption). Holds keep only `snapshot()` and `restore()` for world changes. Initial sending and re-sending after join or server move are handlers on `Added<H>` (see hold hooks).
- Meaning decides where a change runs: a change with a different effect at the packet than at the Paper event means two events (`ClientPosition` is a fake view on the wire, `PlayerMove` really moves). The same effect (`ArmSwing`) means one event: the first source starts the occurrence, the others join it. Nothing may rely on the packet arriving before the Paper event.
- Threads: packets are never held. Verdicts on wire events read only network safe data (stored values, holds, formulas); live access is only allowed on world events, on the thread that owns the identity. Codegen rejects violations. (Research: PacketEvents has no hold API, holding stalls input and confuses anticheats, Paper and Folia already hop once.)
- Occurrence dedupe key: (connection, kind, client sequence number) when the packet has one, otherwise per connection order. Never timing or same tick guesses.
- Requirement (rejected first shape; met by the meaning rule and the codegen thread check above): event capabilities and threads must be typed and checked at build time, but must NOT cause duplicate near-equal events (one for the Paper event, one for the packet).
- Hold hooks: the hold type keeps only snapshot dependent code: `snapshot()` (once, stored snapshot with everything to restore, e.g. location, flight, velocity) and `restore(snapshot)` (once, at the end). Everything that does not depend on the snapshot is a normal handler on `Added<H>` and `Removed<H>`, which fire per live connection of the holder (first start, server move, rejoin); adoption within grace fires neither.
- `Snapshot<H>` parameter: read and update a hold's stored snapshot (for example change where the camera lands, giving one teleport).
- Actions, steps and triggers share one flow: the core emits `Triggered<E>(entry, group, context)` when a chain triggers an entry; the entry is a field of the event. Links always fire explicitly (`entry.triggers.fire(context)`), for actions, steps and triggers alike; nothing follows links automatically. A step entry's handler calls `startStep`; whoever ends the step fires the next links.
- `Runtime<L>`: a live object on one server, never stored, closed automatically with what created it (for example a hold on this server), re-created after a server move through `Added<H>`. Returned from a handler to create it, asked for as a parameter to use it.
- Scope widened (2026-10-29): the primitives should express all legacy systems (audiences, entities and NPCs, sidebars, cinematics, dialogues, bounds), not only events, so there is no separate audience or entity system.
- Chain flow: links fire, not entries: `entry.triggers.fire(...)`, `entry.triggers.random(seed).fire(...)`, `chosen.link.fire(...)`. Firing emits an ordinary `Triggered<T>` event per linked entry, queued like `emit`. Steps start with `startStep(...)` and end with `step.end()`.
- Context: a typed bag of produced records that always passes through; it can only grow, never shrink. Steps keep their context on the step (stored, moves) and can add to it while running. Two kinds of records, like legacy `InteractionContext`: entry records keyed by producing entry plus type (`{smith_question.chosen.index}`, short form `{chosen.index}` when only one is reachable), and global records keyed by type only, about the chain as a whole (legacy: random seed, interacting entity instance, protagonist position override).
- Global records may be replaced (newest wins), never removed; entry records are add only.
- Legacy `PlayerPositionOverride` leaves context: a formula member reads the hold (`protagonist.position` is the camera position while `CameraHold`), so it disappears with the hold.
- State change starts: `@Derive` functions return a stored value or null; the stored value is the snapshot (survives moves, rejoins, multiple servers). Equal result does nothing; otherwise one stored write. Every stored value (derived, attached by a step, or by code) emits `Added<T>`, `Removed<T>`, `Changed<T>(old, new)`. Formulas stay pure values without snapshot; a `@Derive` with a `Hold` result is the same shape, live.
- Identity resolution: a stored value declares the identity kind it lives on (`Mood : Stored<Npc>`). A parameter resolves from the subject, else from the event's only field of that kind. When an event has two fields of one kind, they carry typed roles (`@As(Killer::class)`) and handlers use `@From(Killer::class)`. (Replaces `@From(Event::field)`, which Kotlin cannot compile.)
- Correction: audiences and objectives are NOT just formulas. They stay their own entry systems with the same user visible behaviour as legacy (audience trees with enter and leave, children, inversion; objectives with display, tracking, progress). Only their legacy criteria become formulas. Derived stored values are a building block for them, not a replacement.
- Hold lifecycle unified with stored values: `Added<H>`, `Removed<H>`, `Changed<H>(old, new)` replace `HoldStarted`, `HoldStopped`, `HoldChanged`. For holds they fire per live connection of the holder (start, move, rejoin); the type parameter says which. Changed defaults to remove plus add when nobody handles it.
- Keyed holds: `@Key` on a hold field lets one holder hold many of one type (one `NpcView` per NPC).
- Same hold type, holder and key from several derives: highest priority wins (priority from the derive's entry); a tie is a check diagnostic. Replaces legacy priority audiences and tab list priority.
- Handler parameter kinds (decided below: one `ParameterKind` interface) (plain `Stored` and `Hold` types, Runtime, Candidate, Member, Formula, Near, Nearest, ...) should come from one extensible mechanism, definable by core, capabilities, engines, and extensions.
- Live data never notifies. Normal handlers turn live facts into tracked data (`Runtime` or stored values); everything downstream recomputes automatically. Changes without an event are found by looking, with a handler on an ordinary event such as `Tick`. Refinements: `Unit` handlers run after the outcome is applied (the source decides when); returning a `Runtime` replaces the previous one of that type, and a different value counts as a change.
- Commands (configured-event and `@Command` data class shapes were rejected as too narrow; the command shape below is current). Required: legacy 1 to 9 (any tree shape in code and content, self or others, suggestions from state, console sender, detect and cancel other plugins' commands, block during interactions and re-run, run commands, hot publish) plus: available only during an interaction (`/accept` during an offer), state dependent (`/claim` while a reward waits), same name from two books resolved by priority. Not needed: outside world running commands. New requirement: a command can trigger for another player, and also for the caller while keeping a player argument usable in formulas and context (who it runs for is separate from player arguments). Command contributions merge into one tree per player: no path or branch concept; a root command is just a literal node; each contribution inserts its nodes where they match existing ones and removing it prunes nodes left with no executable and no children. Content custom commands are manifest (audience) entries, not sequence triggers. Prefer structured data over lambdas, with more help from codegen. Command shape: a contribution is a data class whose `nodes` are built with a small data DSL (`literal`, `argument`, `runs<Event>()`); a node that can run names a typed event whose fields are filled from the path arguments by name, checked by KSP on every path. Same literal or same argument name and type merge; two runs at one node use hold priority. Contributions come from derives (`MerchantOffer`, `Candidate<CustomCommandEntry>`, ...). Content: `CustomCommandEntry` and its argument entries build the nodes; a node with triggers runs `ContentCommandRan(node, args)`, whose handler fires the node triggers with the arguments as context. Open: what `force` does for `/tw fire`. `/tw fire` takes the target first (`/tw fire <player> <entry>`) so suggestions follow the target. Direction: a command is a hold (exists for a player now, from a derive), an event (ran, can be denied), and data (the tree). Commands from a book that does not apply to a player are hidden for that player (Brigadier `requires`), the tree is resent when applicability changes.
- NPC scope is who holds the `NpcRunning` hold (server = shared, group = per group, protagonist = individual). The running activity state is a `Runtime` created on `Added<NpcRunning>`, never saved: a restart or a server move starts a fresh activity (like legacy).
- Preview and recording: content mode adds a `Simulating(mode)` stored value to the previewed step. Default is opt-out like legacy: handlers run for real during a preview unless they check `Simulating?` (camera shows a preview display, blinding shows nothing).
- Configured events: an event type may take a configuration type parameter (`Tick<C : TickConfig>`, `RegionEntered<C>`); the source only emits for matching configurations and passes the configuration as `config`. A configuration is a Kotlin object (code) or an entry type (content: one configuration per published entry). Derived events (a handler that `emit`s a narrower event) and configured events are both filters, without a filter concept. Generic mechanism: KSP indexes (event, config type) per handler; publication turns each into config instances (object: one; entry type: every published entry), live across hot publish; the source receives them as a live set (`ConfiguredSource<E, C>.open(configs: LiveSet<C>)`) and indexes them its own way (timing wheel, map by region). Configs a source cannot index are not configured events: use `Candidate<E>` plus an `if` in the handler; entries stay pure data.
- Future engines check (panel engine, Hytale): none of the 7 primitives is Minecraft shaped. `Tick` is a capability, not core. Tracked inputs for formulas and derives must be an extensible set of sources (the panel engine needs draft content). Hold lifecycle runs per live connection of the holder (a Minecraft server session, a browser tab), not per server. Engines meet only through stored state in the realm; interactions do not span engines.
- Primitive set (feasibility, 7, updated 2026-10-30): Event + Source (sources receive `Demand<C>`); Handler (returns the value it produces; parameters resolve through a small fixed core set; demand is computed from handler parameters); Identity + Stored (keys live in `stored(name, keys, value)`; `Due` is an ordinary stored value plus a core source); Derive (result type decides: `Stored` saved, `Hold` live with priority, grace, snapshot and restore, `Live` a computed mirror; the former `@Effect` is merged into `@Derive`); Runtime (local values, never saved: `Runtime` objects with a creator lifetime and `Live` mirrors with a demand lifetime); Formula (with `dynamic()`, `Var<T, C>`, `Changes`, read tracking); Chain. Removed or merged: `ParameterKind`, `@ParameterKind`, `LiveSet`, `Nearest`, `Near`, enter/exit events, the live resolver layer, `Produces<T>`, `member()`, fixed realm scope rules, visibility, `KeyKind`, `VariableValue`, expiry on stored values.
- There is no rule entry concept. Rule control is a cancelable event entry like legacy (`BlockBreakEventEntry(..., cancel: Var<Boolean>)`): a Verdict handler denies when `cancel` holds and fires the triggers in the deny follow up; a Unit handler fires the triggers when the event was allowed. Either way the triggers fire once. With follow ups on every verdict this is one handler: `if (cancel) deny { fire } else pass { fire }`.
- Hot publish: content is a tracked input; step data the protagonist sees is a derive over the step marker plus the entry, so a publish reruns it with no `Republished` event. The step marker stores only moments (`startedAt`). Text is live: the earlier rule "creator fields evaluated once at step start" is dropped. Spoken dialogue: `Speaking(entry, startedAt) : Stored<Step>`, `@Derive fun Speaking.show(...): DialogueHold`, typing via `Tick` over `DialogueHold`.
- Hot publish (identity): an identity defined by an entry ends when that entry is removed.
- The vision is a wish list, not fixed naming or mechanics. When the design finds something better, update `docs/vision/` to match.
- A new concept is only accepted when it is (1) useful in several unrelated scenarios and (2) not expressible another way, or much more ergonomic than the alternative.
- Entries keep the v1 shape (`@TypewriterType`, `@TypewriterDisplay`, `page`, `placement`, relation refs, presentation object). The event system adds behaviour next to them, not a new entry style.

- Leaving and returning: Holds need nothing (connection closes, `Removed`; rejoin, derives rerun, `Added`). Running steps follow a step entry field `onRejoin: Drop | RestartStep | RestartInteraction` (default Drop, like legacy teardown on quit), the same pattern as `onClash`. RestartStep starts the stored step again with its stored context (new `startedAt`), which is a real resume because steps store moments, not progress. Several branches: the strictest wins (Drop > RestartInteraction > RestartStep).

- Step rules are explicit `startStep` arguments: `startStep(context, marker, onClash = entry.onClash, onRejoin = entry.onRejoin)`. A handler may hardcode them (a cinematic passes `onRejoin = Drop` with no panel field); omitted means the default. `startStep` stores a core `StepState(entry, context, onClash, onRejoin) : Stored<Step>`, because the rules must survive the protagonist being gone. Clash reads the incoming rule from the arguments and the running rules from their `StepState`.
- Return is one core handler: `ProtagonistJoined.rejoin(interaction: InteractionState, steps: All<StepState>)` takes the strictest `onRejoin`; RestartStep emits `Triggered(state.entry, state.context)` again, so extensions write nothing for resume. While the protagonist is away, live handlers simply do not apply (their parameters cannot be resolved).
- Group interactions pause only when every member is gone. While one member stays the interaction keeps running; a leaving member's Holds are removed and `Member<P>` handlers skip them; on rejoin their derives rerun and they see the current step. `advance = Everyone` counts online members only. `onRejoin` applies only after all members left.

- Naming: `Protagonist` is the identity (engine neutral, owns stored data, also the panel user); `Player` is only a Minecraft capability trait or part of a Minecraft event name (`PlayerMove`). Core events say protagonist (`ProtagonistJoined`).
- Handler parameters take plain types: a `Stored` or `Hold` type as a parameter is the requirement, nullable means optional, the owner identity is its own parameter (`fun Tick<EveryTick>.type(speaking: Speaking, dialogue: DialogueHold, step: Step)`; optional: `preview: Simulating?`). No `Present<P>` or `Held<H>` wrappers. Derive functions use the stored type as receiver: `@Derive fun Speaking.show(...): DialogueHold`.
- Renames (2026-10-29): Presence to `Stored`, Unit (the running group of steps; Kotlin's `Unit` return type stays) to `Interaction`, `Connected` to `ProtagonistJoined`, `@Effect` to `@Derive`, Attached/Detached/Replaced to `Added/Removed/Changed`, remember/release to `snapshot()/restore()`, Local to `Runtime`, Applicable to `Candidate`, onReturn to `onRejoin`, records to `StepState`/`InteractionState`.

- `Stored` is the data storage vision's stored value plus an owner (its lifetime), so there is one storage concept.
- A server move is a leave and a rejoin; the step entry's `onRejoin` applies. No `Continue` choice and no separate follow setting.
- A suspending handler is cancelled when any value it resolved through a parameter is removed (step ended, stored value removed, member gone). Stale writes are also dropped by the generation check.
- No order among handlers reacting to the same event (stable in practice, not promised); order between events comes from the queue.
- Parameter kinds: one interface for every finder, core included: `interface ParameterKind<T> { fun resolve(event: Event, scope: ResolveScope): LiveSet<T> }`. 0 values skips the handler, many runs it per value, a value ending cancels a suspended handler. KSP checks every handler parameter has a kind. Live capability traits are a finder provided by the engine (`PaperProtagonist : Player, HasChat, ...`); optional capabilities are plain Kotlin type checks.
- Scale: a finder costs about the values it finds; stored types are indexed per type; derives rerun only on input change; `Candidate<E>` scans entries of type `E`, like legacy `Query<Entry>`.

- A finder declares its needs as function parameters, resolved by other finders with the same rules; KSP reads the signature and generates the wiring: `@ParameterKind fun nearestNpc(from: Protagonist, npcs: All<Npc>): Nearest<Npc>? = ...`. Return type gives the count: `T?` 0 or 1, `T` exactly 1, `LiveSet<T>` many. An unmet need is a build error (`Tick<EveryTick>.greet(npc: Nearest<Npc>)` has no Protagonist). World events have a protagonist subject; chain events (`Triggered<E>`) have a group subject, so protagonist finders there need `Member<P>`.
- Groups are being redesigned (not legacy's key function only). Agreed direction: Grouping = a way to bucket protagonists; Group = identity (grouping, key) with stored data and derived members; chains start for one protagonist and widening is explicit, making one shared interaction (not N copies); a stored value names its grouping. Party is not a Typewriter concept.

- Group membership is stored: a grouping is a `Membership` stored value on the protagonist whose value is the key (`Island(@Key who: Protagonist, id)`), kept in sync by handlers or a derive. Works offline (last group), member lookup is an index, visible in the panel. Formulas name the grouping (`player.island`); there is no ambiguous `player.group`.
- Stored keys: a stored value is about 0, 1 or many identities, marked with `@Key` fields inside the value (`Friendship(@Key a: Protagonist, @Key b: Protagonist, level)`, `QuestStage(@Key quest: Ref<QuestEntry>, @Key who: Group<...>, stage)`, no key = global). This supersedes `Stored<Owner>` and the separate owner idea: a value is removed when any key identity ends. Every key must resolve for a handler parameter; same type keys use typed roles. Older sketches written `X : Stored<Step>` mean one `@Key` field of that identity. Symmetric keys are `Set` keys (`Friendship(@Key pair: Set<Protagonist>, level)`): order free, any size, removed when any member ends, filled from all event fields of that kind, stored sorted. Separate keys stay ordered (`Debt(@Key from, @Key to, amount)`).

- Groupings are static group entries (like legacy `GroupEntry`). Core stores one `Membership(@Key grouping: Ref<GroupEntry>, @Key who: Protagonist, key: String)`; a group identity is (group entry, key), e.g. `Group(islands, "42")`. Each group entry kind syncs membership with normal tools (Skyblock: handler on the plugin event; placeholder and world: a derive). New `ManualGroupEntry` changes only through `JoinGroup` / `LeaveGroup` actions, so creators can build parties with data. This refines the earlier `Island : Membership` sketch.
- Widening: `entry.triggers.fire(context, for = group)` starts one shared interaction; default is the current subject. Basic action entries: `ContinueForGroup(grouping)` fires once per distinct group of the members; `ContinueForEachMember` makes copies like legacy `GroupTriggerActionEntry`; `ContinueForEveryone(who: formula)` evaluates the list, creates a snapshot group keyed by the new interaction (ends with it), with fixed members. Book narrowing happens inside `fire`.
- Members of a group interaction are live: derived from `Membership`, a tracked input. A member who leaves the group drops out (Holds removed, `Member<P>` handlers stop); a member who joins sees the current step (derives rerun). Snapshot groups stay fixed by design.

- Offline changes (panel edit while the protagonist is offline): stored only derives and handlers run on any engine that runs the book (the realm picks one; catch up when one starts). Live reactions to a moment can be missed, so the guideline is "store what is owed, not what happened": a derive produces owed state (`SwordOwed`), and a live handler on `Added<SwordOwed>` acts when the protagonist is online (also on join). A realm check warns about live handlers on `Changed<X>` when X can change offline. No replay of missed events.

- Formula field kinds (decided): one field kind `Var<T, C>`; the field text is only the expression (no `amount =`). What T is decides what the text may be: a plain type, a function type (text is the body, parameters in scope, a constant ignores them), or `Changes` (`+=` / `=` on a `Settable` return changes; the entry applies them, so formulas stay side effect free; assigning in a verdict is a type error).
- Book variables (decided): `Book` is a `Resource` (v1 `LibraryModel.kt`), not an entry. Variables are a field on it, `variables: Map<String, Type>`; key rules use the existing configuration system (`BookConfiguration`), no new name type (snake_case later dropped, see names). Function types become a catalog type (`FunctionTypeTemplate { parameters: [name, type], result }`) with multiple named parameters; editor design later. Instances are a field on the book itself (decided, replaces an earlier separate `BookInstance` resource): `Book<V : Record>` is generic, never naming a concrete variables type; `instances: Var<Map<String, V>, BookScope>`, where V is the record type the realm derives from `book.variables` (Bounty board gives `BountyBoardVariables { town: Town; reward: (player: Player) -> Int }`). Plain mode is the normal map editor whose values are real records (one field per variable, right editor, checked by `ValueAdmission`); formula mode generates the instances (`towns.associate { it.id to BountyBoardVariables(town = it) }`), so no separate formula field exists. The map key is the instance key (any name, see names). V is bound automatically (decided): the live `dynamic()` hook gets a `bind` builder, `bind(V) { for ((name, variable) in variables) { val type = variable.type.valueOrNull() ?: continue; field(name, type, hasDefault = variable.default != null) } }`. KSP generates a handle per type parameter; a bound parameter is derived (no picker), an unbound one stays creator picked through `TypeSelection`. - Formulas are a separate system from v1's portable expressions (which have no roots, no members on types, no per field context). Goal: for every formula field the realm knows statically which roots exist. Requirements: (1) roots per field; (2) members on types from many contributors (capabilities, entries, stored values); (3) members generated from content (`dragon_quest.stages.forge_sword`); (4) creator defined record types, used for custom stored data (stored as generic map data); (5) field kinds: `Var<T, C>` value, book variables of function type (the book declares `reward: (player: Player) -> Int`, each instance supplies a formula or a constant like 12, the book uses `book.reward`), creator defined functions; (6) functions as values, lambdas, receiver sugar; (7) implicit arguments; (8) update fields replace legacy modifiers: they may set and update stored values only, never world actions like giving items (those stay explicit entries); conditions, text, verdicts and derives stay pure; (9) visibility and imports across books; (10) engine only live members.
- Formula direction (liked, details pending): three primitives, types, functions whose parameters are filled from scope by type (same rule as handler parameters) or passed explicitly, and scope (typed values; lambdas and blocks stack more). A field declares only what it provides (`Var<String, PlayerContext>`); the realm adds what it statically knows there (book, entry, chain context, capability roots). Sugar: no prefix for what is in scope, no parentheses when nothing is left to pass. Members come from code per type, like presentations: a KSP generated `XFormulaProvider`; static members are plain Kotlin functions in it (signature = declaration, parameters = needs); dynamic members from content via typed builders in `XContent.dynamic()`; defaults are the fields; a same name function replaces; `hidden` hides. `Produces<T>` generates `produced(chain)` and forwards members. The realm runs `dynamic()` at publish for names and types; engines run the same code at load; evaluation calls the Kotlin function or returns the registered value. The realm can evaluate formulas that need no engine type. Refinements: `dynamic()` runs live on the realm (no publish) over a KSP generated content view of raw data (each field value, missing or invalid), never the real entry class, so a broken field only drops its own members. Capabilities declare formula functions as interfaces; engines implement them (`PaperPlayerFormulas`), and KSP checks completeness. The standard library is providers too (`Int.plus`, `List<T>.sumOf(f: (T) -> Int)`): needs generics, function parameters, operators as sugar, and lambda parameters pushed as scope levels. Formulas are NOT v1 expressions: expressions encode portable operations the panel must perform; formulas get their own interpreter in the engine core (parse text, bind names, run, cache outcomes). Do not reuse the expression AST (`ExpressionNode`) or `PortableExpressionChecker` for formulas. Narrow reuse (decided): the standard library is generated from `operations.yaml` into a stdlib formula provider that calls the existing Kotlin kernel (`operator fun Int.plus(other: Int) = PortableKernel.numberAdd(this, other)`), with a mapping layer; `XFormulaProvider` follows the presentation codegen pattern (new emitter, loaded by `GeneratedProviderLoader`); formula types are described with `TypeDefinition` (no id or revision); the content view for `dynamic()` is `XDraft` (verify it models invalid values, else extend it). Rejected: fixed realm rules, `@Name`, layers, Kotlin `context(...)` declarations, per entry generated functions.

## Type glossary (new types from the formula and variable work)

| Type | Kind | Purpose |
| --- | --- | --- |
| `StaticEntry` | interface, extends `Entry` | An entry that declares something (data, definitions) and is never triggered. |
| `Variable<K, T>` | static entry | Creator declared stored data: `keys` (record K of identity types), `type` (T), `default`, `reactions`. Its `dynamic()` binds K and T and calls `stored(name, keys = K, value = T, default)`. |
| `Identity` | catalog parent type | Marks types allowed as key fields: `Protagonist`, `Interaction`, `Session`, any entry `Ref`, `ItemRef`, group identity types exported by group entries. |
| `Session` | identity | One connection of a protagonist, id supplied by the engine kind (Minecraft proxy connection, panel tab); survives server moves and reloads; ends after a grace with no engine reporting it. A protagonist may have several. |
| `ItemRef<X>` | identity | Reference to one item of a list field inside an entry, by v1 `ItemId`; ends when the item is removed. |
| `Settable<T>` | formula type | A stored value at specific keys that can be read and changed; generated from `stored()`. |
| `Change`, `Changes` | values | One or more storage operations (set, add, append, remove, put, clear, multiply, max/min, setIfAbsent, require, ...); `apply()` commits them as one optimistic transaction. |
| `Reaction<K, T>` | polymorphic interface | Behaviour attached to a variable; has `changes: Var<Changes, ReactionScope<K, T>>`. Each kind is a type plus handlers in an extension. |
| `ReactionScope<K, T>` | data class | Formula scope of a reaction: `keys: K`, `value: Settable<T>`, `previous: T?`. |
| `Due<E>` | core stored value | Durable time: `Due(@Key event: E, at)`; the core timer source emits `event` once when `at` passes (catching up after downtime) and removes the Due. |
| `AfterWrite<K, T>` | reaction | Runs its changes `duration` after the first or last write (`from: Write`). |
| `Write` | enum | `First` or `Last`. |
| `AfterWriteElapsed<K>` | event | Emitted through a `Due` when an AfterWrite deadline passes; fields `variable`, `keys`, `reaction` (all identities). |
| `Every<K, T>` | reaction | Runs its changes for every stored key on a cron schedule. |
| `EveryElapsed` | event | Emitted through a `Due` when an Every schedule fires; fields `variable`, `reaction`. |
| `Definition<T>` | static entry | Shared named value of any type (including function types): `name`, `type`, `value`. |
| `Live` | marker interface | Immutable mirror value of live engine state, keyed by identities, never saved, maintained only while demanded. |
| `Seed<X>` | core event | Emitted when mirror X is first needed for an identity; its handler reads the current value once. |
| `Because` | enum | `Value` or `Tracking`, on `Added`/`Removed`: whether the value really appeared or vanished, or tracking started or stopped. |
| `FormulaChanged<T>` | event | A watched formula's result changed: `entry`, `subject`, `old`, `new`. |
| `SessionReporter` | engine contract | How an engine reports connections: `connected(protagonist, id)`, `disconnected(id)`. |
| `Demanded<X>` | core parameter | The keys of mirror X demanded for the handler's subject right now; producers check only those. |
| `Demand<C>` | core source input | The configs of a configured event that currently have a runnable handler; replaces `LiveSet<C>` in `ConfiguredSource.open`. |
| `Indexed` | marker interface on a `Live` type | The engine reports its `Added`/`Removed` to the realm, which keeps an online index for the session. |
| `XMigrations` | generated hook per type | `migrate()` compares the last published view (`old`) with the draft (`new`), asks inputs, and produces `Changes` run at publication. |
| `PendingMigration` | core resource | Holds a migration's creator inputs as ordinary content; unfinished inputs block publication. |
| `OnWrite<K, T>` | reaction | Runs its changes inside every write's own transaction: rewrite, guard (`require`), write other values, trim. |
| `At<K, T>` | reaction | Runs its changes at `at: Var<Instant, ReactionScope<K, T>>`, computed from the value and re-armed on each write. |
| `AtElapsed<K>` | event | Emitted through a `Due` when an At time passes; fields `variable`, `keys`, `reaction`. |
| `EveryRan` | stored value | Last run time of one Every reaction, keyed by the reaction item (one per Every reaction, removed with it). |
